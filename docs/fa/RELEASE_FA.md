# نسخه‌بندی و انتشار — StreamGuard (نسخهٔ فارسی)

این سند فرایند انتشار، قانون «تست ناموفق = بدون انتشار» و فهرست آرتیفکت‌ها را توضیح
می‌دهد.

نسخهٔ انگلیسی مرجع: `CHANGELOG.md` در ریشهٔ مخزن (تاریخچهٔ مرحله‌ای v1.x تا v10.3.2) و
[CONTRIBUTING.md](../../CONTRIBUTING.md) §Release process — مطالعهٔ مرتبط:
[TESTING_FA.md](TESTING_FA.md) و [DEVELOPMENT_FA.md](DEVELOPMENT_FA.md).

## نسخه‌بندی مرحله‌ای

توسعهٔ مخزن با ده نسلِ مرحله‌ای جلو رفت و در پایان به نسخهٔ **v10.3.2** رسید. مرجع
کاملِ «در هر نسخه واقعاً چه چیزی تغییر کرد» فایل `CHANGELOG.md` است — فهرست مدخل‌های
آن، همان داستان مرحله‌ای این مخزن است و این سند آن را بازنویسی یا تکرار نمی‌کند. نسخهٔ
جاری v10.3.2 در همهٔ فراداده‌ها (Go/Python/TS) و در هدر `X-StreamGuard-Version` همهٔ
پاسخ‌ها یکسان است. گردش کار انتشار، برچسب را با سرِ `CHANGELOG.md` مطابقت می‌دهد؛
برچسبِ جلوتر از CHANGELOG رد می‌شود.

## قانون طلایی

**تستِ الزامیِ ناموفق = بدون انتشار.** گردش کار انتشار، کل مجموعهٔ تست را اجرا می‌کند؛
هر شکستی مسیر را متوقف می‌کند. همچنین برچسب (tag) باید با سرِ `CHANGELOG.md` مطابقت
داشته باشد — برچسبِ جلوتر از CHANGELOG رد می‌شود.

## فرایند انتشار (خودکار با `.github/workflows/release.yml`)

1. **اعتبارسنجی:** برچسب با `CHANGELOG.md` تطبیق داده می‌شود؛ ساخت وب (lint + tsc) و
   مجموعهٔ کامل تست‌ها اجرا می‌شود.
2. **ساخت آرتیفکت‌ها** (بند بعد).
3. **SHA256SUMS:** برای همهٔ فایل‌های توزیع، `sha256sum` تولید و در فایل
   `SHA256SUMS.txt` کنار آرتیفکت‌ها منتشر می‌شود.
4. **SBOM:** فهرست اجزای نرم‌افزار با قالب SPDX-JSON (anchore/sbom-action) ساخته و
   بارگذاری می‌شود.
5. **GitHub Release:** آرتیفکت‌ها + `SHA256SUMS.txt` + SBOM به‌عنوان انتشارِ برچسب
   منتشر می‌شود.

## آرتیفکت‌ها

| آرتیفکت | شرح |
|---|---|
| باینری‌های Go چندسکویی | `sg-ingestor` و `sggen` برای linux/amd64، linux/arm64، darwin/amd64، darwin/arm64 (ساخت `CGO_ENABLED=0` با `-trimpath` و `-ldflags="-s -w"`) |
| کتابخانهٔ پارسر C++ | `libsgparser.a` (استاتیک) + `libsgcapi.so` (C ABI) + `PARSER_README.md` |
| sdist پایتون | بستهٔ `streamguard-analytics` با `python -m build --sdist` |

## چک‌لیست نگهدارنده (پیش از هر انتشار)

- فرادادهٔ نسخه در همهٔ اجزا به‌روز باشد و با سرِ `CHANGELOG.md` یکی باشد.
- کل مجموعهٔ تست سبز: `make test`، `make sanitize`، `make e2e` و jobهای CI.
- `CHANGELOG.md` مدخل نسخهٔ جدید را صادقانه توصیف کند (چه کردیم/چه نکردیم).
- برچسب `vN.N.N` بزنید و بگذارید گردش کار، اعتبارسنجی تا انتشار را انجام دهد.

## تأیید آرتیفکت پس از دانلود

گیرندهٔ انتشار می‌تواند یکپارچگی فایل‌ها را خودش بسنجد — این دقیقاً دلیل وجود
`SHA256SUMS.txt` است:

```bash
sha256sum -c SHA256SUMS.txt        # باید برای همهٔ فایل‌ها OK بدهد
```

SBOM (`sbom-spdx.json`) هم اجزای نرم‌افزاریِ هر آرتیفکت را فهرست می‌کند؛ برای ممیزی
زنجیرهٔ تأمین، همان فایل مبنای بررسی است. هر دو قلم در ضمائم همان GitHub Release
منتشر می‌شوند.

## یادداشت صادقانه

- «انتشار» یعنی همان آرتیفکت‌هایی که در بالا آمده؛ هیچ بستهٔ بسته‌بندی توزیع‌ها (deb/rpm)
  در این مرحله وجود ندارد و ادعایی هم مطرح نمی‌شود.
- آزمون یکپارچگی PostgreSQL در CI انجام می‌شود؛ اگر CI در دسترس نبود، انتشار انجام
  نمی‌شود — همان قانون طلایی.
